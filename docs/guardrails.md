# Milestones, escalations and guardrails

## Milestones

The human hears from the orchestrator at four milestones only:

1. setup done;
2. concepts chosen;
3. finalists clickable;
4. deck ready.

Each milestone report is short: what is done, what it cost so far, where to look.

## Escalations

Only these interrupt the human between milestones:

- anything that changes an already-made decision in the contract;
- a change to shared code outside the screen's scope;
- costs far above the plan;
- anything outside the guardrails.

Everything else, the orchestrator decides, logs in the status board with its reason, and goes on. Leads escalate
the same four things to the orchestrator, and decide everything else themselves.

Permission prompts are not escalations; they always go to the human. When a lead stalls at one, the multiplexer
shows it as `blocked`. The orchestrator tells the human which tab and what the lead needs. It never answers the
prompt itself, and no message can.

One example from our run: a lead found a bug in a shared styling helper that made custom font sizes fall back to the
default across the whole app. That is shared code outside scope, so it went to the human. The human decided: a
separate branch and merge request, outside the design run. The designs worked around the bug in the meantime.

## Guardrails

| Rule | Why |
|---|---|
| No push, no merge request, no comments on the code host or ticket system from any agent | The human publishes |
| No dependency installs | Supply chain and registry rules; worktrees share one lockfile |
| Apps start and stop only through one sanctioned launcher script, owned by the orchestrator | A restart changes seeded ids and breaks running walks |
| Never touch the development database | Walks and tests use their own seeded databases |
| Walkers, judges and recorders never change data | Every walk must see the same data; some buttons start real jobs |
| Leads write only in their worktree and their run folder | Leads run in parallel in sibling worktrees |
| No permission bypass | The human stays the last check |
| No bare `git stash` | The stash stack is shared across all worktrees of a repo |

## Hooks that enforce them

Each lead gets its own settings file, generated by a small script and stored outside every worktree. It holds a
deny list (`git push`, the code host CLIs) and these hooks:

| Hook | What it does | Why |
|---|---|---|
| PreToolUse on Bash | Denies push, stash, host CLIs, installs, `npx`, app start and stop, permission bypass, by regex over the whole command | A rule like `Bash(git push *)` misses `git -C . push` or `bash -c "git push"` |
| PreToolUse on Edit and Write | Denies paths outside the lead's worktree, its run folder and `/tmp` | Leads stay in their lane |
| PostToolUse on Edit and Write | Runs the linter on the changed file and sends errors back to the model | Mistakes caught at once; the typecheck runs at the gate |
| Stop | Blocks the lead from ending its turn until its status file has `phase:` and `gate:` lines and is newer than its latest commit or change. Lets go after 3 blocks | No silent "done"; no endless loop |
| Critic evidence | Blocks a critic's report until every screenshot it names exists and is not empty. Lets go after 2 blocks; a report marked `DEGRADED` passes | No walk without evidence |

Known limits, accepted because the sessions are cooperative:

- The path guard sees only Edit and Write. A shell `cp` or redirect passes it.
- The hooks are a seat belt, not a sandbox. The push guard and the deny list are the hard line.

Test one hook of each kind in a throwaway headless session before relying on it. In our run, one test showed that a
`SubagentStop` block did not reach the critic in the Claude Code version we ran. A subagent hands its report back
through a tool call, so the evidence check had to run on `PreToolUse` for that call. `SubagentStop` stayed as a
backstop. Check this against your version.
